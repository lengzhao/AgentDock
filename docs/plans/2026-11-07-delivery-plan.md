# AgentDock 分阶段交付计划

日期：2026-11-07。状态：需求与技术验证计划草案。本文不启动编码、创建平台应用或发布软件。

**目标**：在 macOS 上，用户完成引导后，通过 Lark 使用已有 Agent，并能可靠地管理后台服务和修复故障。

**架构方向**：独立 Go 产品，基于 AgentKit；官方 Lark SDK 用于平台能力，`go-keyring` 存储敏感凭据，launchd 管理用户级服务；不依赖 agent-harness。

**首批建议**：Claude Code + Codex；具体版本、最低 macOS 版本与打包方式由 M0 验证确定。长期主流 IM 与跨系统目标保留，首版只验收 macOS + Lark。

## 1. 计划原则与依赖

顺序为 M0 可行性 → M1 最小运行闭环 → M2 用户引导与凭据 → M3 后台可靠性 → M4 发行验收。M0 未通过的能力不能进入已支持列表。

暂不承诺日历工期。完成 M0 后，根据依赖缺口、平台授权等待和 Agent 兼容成本估算；将人工审批等待与开发时间分开记录。

本计划定义工作包、文件边界和验收证据。模块通过设计评审后，再拆成具体代码任务；不提前编造 AgentKit 尚未核实的函数签名或依赖版本。

## 2. M0：验证关键可行性并冻结首版设计

### T0.1 Lark 官方扫码注册与消息接入验证

产出：`docs/research/lark-onboarding-validation.md`。

1. 从官方 SDK 发布 tag 核实 `registration.RegisterApp`、所需权限/事件/回调配置及 Lark 国际站入口。
2. 用授权的测试租户验证：扫码、用户拒绝、超时、取消、已有应用接入，以及网络中断后恢复。
3. 检查应用是否需要发布、管理员批准或安装；记录身份前提和失败码，不保存 Secret、授权 URL 或 token。
4. 验证真实收消息、文本回复、卡片审批、图片/文件；记录每项 scope。
5. 确认注册结果不确定时的核对方式，防止重复创建应用。

通过标准：有可复现的官方扫码路径，或有记录清楚的账号/发布版本限制及已有应用接入路径。若扫码不可用，只能说明首版自动注册受限，不能通过改名隐藏差距。

真实创建应用、提交权限、审批和发布属于外部变更，在实施任务中按当时授权执行；当前阶段仅完成方案。

### T0.2 Claude Code 与 Codex 适配验证

产出：`docs/research/agent-compatibility.md`。

分别验证安装路径、登录、版本、ACP 握手、流式文本、权限允许/拒绝、取消、会话恢复、Agent 异常退出、图片和输出文件。确认 Claude SDK 配置加载与登录行为；确认 Codex 适配器实际使用的 CLI，不能只记录用户 PATH 上的版本。

通过标准：至少一个 Agent 全链路通过；第二个 Agent 通过相同核心契约后才能列为正式支持。两者未同时通过时，调整支持范围要写明原因。

### T0.3 AgentKit 复用边界验证

产出：`docs/research/agentkit-integration.md`。

执行前按仓库要求运行 CodeGraph 初始化并优先使用 CodeGraph 分析，核实固定版本的配置装配、平台生命周期、ACP、权限、会话恢复、投递和文件能力。逐项标记“直接复用 / AgentDock 应用逻辑 / AgentKit 通用缺口”。

不得为产品引导把全部安装逻辑塞入 AgentKit，也不得在 AgentDock 复制它已有的消息循环。需要上游改动时单列依赖，不能假定已发布。

### T0.4 macOS、Keychain 与分发验证

产出：`docs/research/macos-service-validation.md`。

验证所选 `go-keyring` 版本在终端与 LaunchAgent 下的写入、回读、首次系统授权、锁定/解锁、凭据轮换与二进制升级行为。分别记录 arm64/x64 的构建与实机证据；模拟器/交叉编译不能冒充实机验证。

核实最低系统版本、Agent 可安装范围、签名/公证与分发要求。决定安装方式、稳定安装路径及包名；检查同名项目造成的混淆。

M0 退出条件：更新需求中的未决项、形成可评审设计，并确定验收矩阵。尚无真实账号或设备时记录验证缺口，不伪造结论。

## 3. M1：最小运行闭环

建议文件边界（均尚不存在，实施时按 M0 结果调整）：

- `go.mod`、`cmd/agentdock/main.go`：固定依赖与命令入口。
- `internal/config/`：配置模型、校验、schema 版本与原子写入。
- `internal/runtime/`：AgentKit 运行与生命周期适配。
- `internal/agents/`：Agent 目录、路径/版本检测与能力声明。
- `internal/state/`：会话、接收去重、任务与投递状态。
- `internal/access/`：所有者、允许用户和请求关联。

工作顺序：

1. 建立前台运行命令和最小配置，使用已有 Agent 与已有 Lark 测试应用。
2. 打通私聊文本 → Agent → 回复，保留结构化事件与明确终态。
3. 增加会话路由、去重和有界队列；固定同会话串行规则。
4. 增加审批允许/拒绝/超时、取消与子进程回收。
5. 增加长文本、图片/文件传入及受限产物回传。
6. 接入第二个通过验证的 Agent，验证接口未偷偷依赖第一种 Agent 的行为。

验证：用 fake Agent/平台验证重复事件、请求关联、并发隔离和终态；用真实 Lark 分别验收两个 Agent。对未知发送结果与任务接收成功但未完成进行故障注入。不写只镜像代码的测试。

M1 退出条件：核心对话和权限闭环可用，尚不宣称一键安装或后台可靠运行。

## 4. M2：配置引导与安全凭据

建议文件：`internal/setup/`、`internal/credentials/`、`internal/platforms/lark/setup.go`、对应 CLI 子命令与用户指南。

工作顺序：

1. 将环境检查、Agent 检测/登录、区域选择、平台注册、绑定和测试定义为可恢复步骤。
2. 封装 Keyring 接口；测试用内存实现，真实 macOS 另做集成验收。
3. 引导敏感输入与扫码流程，保存 Keychain 后回读成功才写配置引用。
4. 支持已有应用，标注必要权限和发布状态，明确扫码路径不可用原因。
5. 完成所有者一次性绑定，拒绝陌生用户抢绑。
6. 用一次性测试消息确认真实端到端成功，保存测试时间和版本信息。
7. 提供凭据检查、重新授权与轮换；诊断不回显秘密。

关键测试：重复运行 setup、不完整配置、Keychain 写入/回读失败、取消扫码、创建应用结果未知、权限不足、过期/重放配对、Secret 更新部分失败。配置写入失败时保留旧有效配置，不自动删除可能仍在使用的凭据。

M2 退出条件：支持的账号条件下，用户无需手改配置即可完成前台首次使用；尚需 M3 服务身份复验。

## 5. M3：后台服务与恢复

建议文件：`internal/service/`、`internal/diagnostics/`、状态存储恢复逻辑、`docs/guides/service.md` 与 `docs/guides/troubleshooting.md`。

工作顺序：

1. 实现用户级 LaunchAgent 的安装、启动、停止、重启、状态和卸载。
2. 固定路径/工作目录与非敏感启动环境；添加单实例锁和子进程生命周期管理。
3. 服务启动后验证 Keychain 可读、Lark 就绪、Agent 可启动与认证有效。
4. 增加网络恢复、崩溃退避、日志轮转、优雅退出与孤儿进程处理。
5. 恢复会话映射和未投递结果；执行中任务标记为中断/未知并按能力核对，不自动重做。
6. 提供分层 status 和 doctor；默认仅非付费检查，真实 Agent 请求另设明确选项。
7. 卸载停止服务并保留用户状态；清除数据/凭据为独立明确操作。

关键测试：终端关闭、重新登录、PATH 变化、Keychain 锁定、断网重连、进程强退、Agent 子进程退出、启动循环、同安装双进程、审批期间停止、执行完成但投递超时。不能只看 launchctl 的注册状态判定健康。

M3 退出条件：真实 LaunchAgent 身份完成端到端对话；所有故障至少有准确状态和修复路径。重启恢复能力按实际支持范围记录。

## 6. M4：打包、发布与验收

建议文件：`.github/workflows/ci.yml`、`.github/workflows/release.yml`、`scripts/`、`docs/guides/install.md`、`docs/compatibility.md`，同步中英文 README。

工作顺序：

1. 固定依赖、构建 arm64/x64 安装产物与校验文件；明确签名/公证状态。
2. 在干净用户环境测试下载、安装、Agent 依赖引导与配置，不要求 Go 或源码目录。
3. 执行全套首版验收矩阵，保存版本化报告，未覆盖组合不列正式支持。
4. 验证升级、配置迁移、升级失败恢复和卸载；不触碰已有 Agent 安装与其他产品凭据。
5. 更新 README 的真实安装命令、限制、兼容版本和修复指南，移除规划占位说明时附验收依据。
6. 对照 cc-connect 做有限流程比较，明确测量条件；结果未支持的差异不进入宣传。

首版发布门槛：P0 全部通过；未解决的丢任务、串会话、越权审批、凭据泄漏和重复外部执行阻止发布。构建成功不能代替真实服务/平台验收。

## 7. 首版验收矩阵

| 维度 | 必验条件 | 证据 |
|---|---|---|
| 环境 | 支持的 macOS 最低/当前版本；arm64/x64 分别记录 | 构建、安装、实机报告 |
| Lark | 国际站；扫码注册与已有应用；私聊和受控群线程 | 应用条件、权限清单、真实消息记录（脱敏） |
| Agent | 每个首发 Agent 的固定 CLI/适配器组合 | 登录、流式、审批、取消、恢复报告 |
| 凭据 | 终端与服务身份；锁定/授权/轮换 | 不含值的检查结果 |
| 消息 | 去重、隔离、限流、长文本、文件、未知发送结果 | fake 故障注入 + 真实验证 |
| 生命周期 | 关闭终端、重新登录、断网、崩溃、升级、卸载 | 状态变化与修复步骤 |

## 8. 后续路线

- 扩展批 A：Slack、Telegram、Discord；Linux 支持；Pi/Grok/Kimi 等新增 Agent。
- 扩展批 B：飞书区域专项认证、钉钉、企业微信、Teams；Windows 服务与凭据。
- 扩展批 C：LINE、WhatsApp、Matrix 等；评估有公网回调和设备桥接要求的平台。
- 体验增强：本地管理 UI、多连接/多工作区、定时任务、主动提醒和可选隔离。

每批先验证平台权限/传输/凭据机制，再复用通用契约。支持状态分为 planned、experimental、verified、blocked；只有带版本与验收证据的组合可称 verified。

## 9. 风险与调整规则

- 自动注册仅默认分支可见：核实 release；必要时等待上游版本或明确标为实验功能。
- AgentKit 缺通用能力：单列上游任务，先评估再排期；不建立永久重复实现。
- Agent 协议漂移：锁定并测版本，升级前回归；不在服务启动时任意拉取 latest。
- 账号/审批阻塞：记录外部前提，不靠扩大权限绕过。
- Keychain 后台不可读：让引导完成系统授权与回读，不保存明文替代。
- 首版范围增加：必须同时补充验收矩阵和时间评估；不让“主流 IM 长期目标”变成首版无限扩张。

本次交付仅为文档。下一步建议从 M0 技术验证开始，在已有授权范围内推进可读检查；真实账号变更和软件实现按后续明确任务执行。
